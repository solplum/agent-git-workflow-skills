# 分叉分支合并

目标：让双方仍然有效的业务能力、约束和修复在整合结果中有可核查的去向，并说明实际验证到哪里。主要场景是主干进入用户自己的功能分支，也支持协作分支整合。适用于公司及个人项目；用户主要负责自己的功能。

核心规则：**双方变化的意图 → 选择整合方式 → 整合后的实现位置 → 各自及组合行为的证据**。按行为保留，允许等价迁移。被明确废弃的行为按当前有效需求处理，并记录依据。代码和功能可以围绕一支统一，再追加另一支有效增量；提交历史不强求线性，具体历史记录方式与代码整合策略分别判断。

## 权限与工作范围

- 默认执行本地分析、合并、必要适配和验证。创建提交、推送、PR、合入共享主干及发布需要本次明确授权；已有明确授权继续有效，无需重复询问。默认也不创建临时提交或 `commit-tree` 对象。
- 自行查清代码、历史、测试和约定能够回答的问题。意图清楚的冲突及维持既有行为所需的局部适配直接处理。缺少业务裁决、需要新规则或扩大功能范围时，带证据、建议和影响集中提问，继续处理独立且安全的部分。
- 公司项目遵循已有需求和责任边界。用户拥有自己的功能，不代表能修改他人负责的共享策略。无法查明的冲突交由用户确认或转交对应负责人。
- 保护已有工作与并行任务。保留他人的改动；不以合并为由执行强推、重置覆盖、清理未跟踪文件、自动 stash、改项目 Git 配置或重写历史。生成文件和锁文件用项目现有工具按最终依赖重建，核对依赖兼容及无关变化。
- 核心工作只依赖 Git 和项目本身的验证工具。按宿主可用能力操作，不依赖 Codex、Claude Code 的专属命令或其他 skill。

## 1. 确认方向，冻结输入

读取会话和仓库规则，检查仓库根目录、当前分支、工作树、暂存区、未跟踪文件、其他 worktree，以及是否已有 merge/rebase/cherry-pick 等操作。记录原始 HEAD、目标分支、来源分支的完整提交 SHA 和来源更新时间；安全执行细节见 [references/git-operations.md](references/git-operations.md)。

优先从当前任务、分支和远端默认分支查明来源。当前分支的 tracking branch 可能只是其同名远端分支，不能据此认定是主干。方向仍有歧义才问一个具体问题；不要重复询问用户已明确的角色或权限。

需要远端最新主干时，定向 fetch 对应远端分支，再冻结得到的 SHA；保留用户指定的固定版本。fetch 失败可继续分析已知快照，但披露来源时效，不能声称已同步最新远端。之后针对冻结版本工作，不在过程中悄悄换来源。

区分交付目标和代码基线：目标是用户要更新的分支及原始 HEAD；基线是承载完整实现的冻结版本，两者可以不同。先记录现状，确定策略后再执行。原生合并在干净且独占的目标工作树可直接准备；基线追加优先使用基于所选基线的隔离 detached worktree。存在脏改动、其他任务、未解业务矛盾，或目标未检出时保留原工作树并隔离候选。明确列出未纳入候选的未提交工作。

已有 merge：检查原始父版本、当前解冲突进度和用户改动后再接手，不重跑合并或覆盖已有解法。已有 rebase 等其他操作：完成只读分析后，针对该操作说明下一步，不自动 abort 或改成 merge。操作状态未厘清时不开始新的合并。

## 2. 建立双方行为清单

用共同祖先、双方独有提交和相对共同祖先的 diff 还原变化，结合必要的需求、提交说明、测试及历史。按功能或约束分组；格式化、生成物等可归并。遇到多个 merge-base，检查历史与 Git 的合并结果，不能随取一个祖先作为唯一事实。

建立简明清单，逐项记录：

| 来源与行为 | 意图依据 | 合并后的实现/处置 | 验证与状态 |
|---|---|---|---|
| 功能分支或来源分支：具体能力、修复、约束 | 文件、测试、需求或提交 | 位置；保留、等价迁移、有意淘汰或待决定 | 实际证据；通过、失败、未验证 |

双方重要变化都需有去向。广泛的主干变化按影响分组：追查与功能分支有交集或依赖的部分，其余说明如何保留及验证覆盖范围，避免把局部检查描述为主干全部功能已验证。

证据不一致时查明约定是否仍适用。分支名称、提交时间、“最新版”和测试数量都不能独自决定哪方正确。新增代码、旧行为、删除和修复都可能承载意图；确认有意删除后保留删除目的，将仍有效的能力迁到合适位置。

## 3. 先选择整合方式，再执行

先根据双方行为清单、包含关系、当前架构和实际契约判断内容是否已覆盖。已覆盖则说明证据及验证范围，无需为了选择方式制造改动。

确需整合时，用户可以自由选择“基线追加”或“原生三方合并”。用户已明确指定方式，按该方向处理并自行调查细节，不重复询问；若所选方式有实质障碍，解释具体原因和替代方案，不能悄悄换方式。用户未指定时，先分析并推荐一种，同时用业务行为说明两种方式在本次任务中的差异、建议基线及影响，**等待用户选择后再开始整合修改**。用户明确要求自动判断并执行，也视为本次已有方式授权。

| 方式 | 适用依据 | 执行目标 |
|---|---|---|
| 完整基线＋有效增量 | 一支已提供适用的完整结构、规则和修复，另一支尚缺的有效变化可识别并迁入 | 围绕基线统一实现，补齐另一支仍需要且未覆盖的功能、修复与约束，以及必要适配 |
| 原生三方合并 | 双方并行变化相互交织、整体合并更直接可靠，或本次任务要求保留真实 merge 状态 | 使用共同祖先和双方版本准备不提交的 merge，逐项审阅自动及手工整合结果 |

基线依据来自本次明确要求、仍适用的架构和业务契约；分支名、提交时间、冲突多少或 diff 大小都不足以单独决定。缺少选择另一侧为基线的依据时可推荐原生三方合并，不用臆造“较新的一方全对”。真正互斥的需求仍需业务裁决，选择追加不能替代该决定。

追加按行为识别增量，同时检查新增、修改、删除、重命名、回退、测试、配置及依赖。追查关联变化，保留基线的有效修复和有意删除目的；迁移增量调用方和约束，避免复活已淘汰实现。另一支的新增文件、独有提交或整份共同祖先 diff 都不直接等于有效增量。

内容候选可以没有 MERGE_HEAD；原生 merge 检查真实 MERGE_HEAD。不要为追加自动 rebase、重写分支或创建提交，也不伪造 merge 状态。执行和候选应用细节见 Git 执行参考。

### 检查组合逻辑并解决冲突

对文本冲突按 base、目标、来源三个版本比较。逐项解释双方为何变化，再实现兼容的行为。使用某一侧内容时，说明另一侧意图如何保留或为何不再适用；避免整文件机械选边、保留两套相互矛盾的实现或删测试换取通过。

同时检查没有文本冲突的交互。沿实际改动涉及的调用链和数据流追查，按适用风险检查：

- 参数、返回值、类型、单位、默认值及错误语义；调用方是否一起更新。
- 权限、过滤、状态转换、异步完成、重试及副作用；双方组合是否破坏约束。
- 已承诺的配置、历史数据、存储格式及旧客户端兼容；迁移、读写和依赖是否配套。
- 接口、界面、CLI、文档、测试和生成物之间是否仍表达同一行为。

只检查与改动有关的关系，不扩展成全仓重构或无关审计。为维持双方既有行为，可调整必要调用方、配置和兼容代码。若两边对同一行为有互斥要求，先查是否属于不同入口、受众或阶段；仍矛盾时标出具体选择及影响，请用户或相应负责人裁决。需要新增模式、公共契约或交互规则时先提出方案。

多来源检查彼此包含关系和有效增量，说明顺序并验证最终组合。可在一份完整基线之上逐步整合内容，也可采用原生多头合并。分别判断代码内容、验证和历史记录的完成度；不能用隐藏提交或内容整合伪装完成合并历史。

## 4. 按行为验证

先识别项目要求的检查和本次真正受影响的行为，执行相关检查；仅在新改动、失败或未解决的疑虑出现后扩大或重复。规模与风险相称，复用现有工具。

关键证据包括：

1. 功能分支新增或修复的关键行为成立。
2. 来源分支在相关范围内新增的能力、修复和约束成立。
3. 双方同时生效时，关键组合场景成立，包括受影响的重要边界和错误路径。

检查预期业务结果。可用现有测试、接口调用、页面操作或定向验证；构建通过和无冲突仅说明其各自覆盖的事实。现有覆盖不足且有明确风险时，补最小必要的回归测试或临时验证脚本。持久测试覆盖可复现的行为风险，临时证据不混入产品代码。

失败先定位来源：本次整合引入或必须解决的问题本次修复；原有独立缺陷记录影响，另行决定处理。必要时在冻结的双方版本分别复现同一检查，使用隔离目录，保持依赖和命令可比。没有复现证据时标“来源未确定”，不要推断为原有问题。

缺少环境、账号或数据时，完成可完成的本地工作，明确哪些关键行为未验证、缺什么、如何补验。可交付本地结果，但保持“验证不完整”的状态。关键业务矛盾未裁决时，交付候选及待决事项，不宣告整合完成。

## 5. 复核并交付

复核最终结果分别相对目标、代码基线和各来源的差异，用行为清单逐项核对。解释重要删除、替换和兼容调整；检查冲突残留、暂存与未暂存变化、未跟踪文件和意外生成物。清理本次引入且无需求的代码、注释或测试；原有无关内容保持原状。

交付前重新核对目标分支、工作树和冻结引用。原目标发生变化时保留候选，重新分析后再应用；其他 worktree 中的独立工作不搬移或覆盖。隔离候选是否已经应用到原目标必须写清楚；直接应用的安全条件见执行参考。

报告默认在回复中给出，内容包括：

- 交付目标、原始 HEAD、所选整合方式与理由、代码基线和各来源冻结 SHA，以及结果所在工作树。
- 双方行为清单，含重要冲突决定和无文本冲突的逻辑适配。
- 实际检查、结果和未验证项；已有问题与本次问题分别说明。
- Git 当前状态：目标及候选 HEAD、是否有真实待提交 merge、是否仅为内容候选、是否已应用目标，以及来源是否已进入目标祖先关系。
- 剩余决定或补验步骤；如用户要继续提交/推送，展示具体范围后依据本次授权执行。

准确使用状态：“本地内容已整合并验证，未提交”“本地候选，验证不完整”“等待业务决定”。追加内容候选可以没有 `MERGE_HEAD`；原生 merge 在默认不提交时保留该状态。候选基于来源时，在候选提交也不等于提交到原目标。明确区分内容完成、验证完成、已应用目标和历史已记录，说明证据支持的结论及实质缺口，不保证未知行为绝对无错。
