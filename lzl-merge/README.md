# lzl-merge

分支分叉后的本地合并与逻辑整合 skill，适用于 Codex 和 Claude Code。

主要用于把主干更新合入自己的功能分支，也支持整合协作分支、接手已有 merge 冲突。先检查内容是否已覆盖；确需整合时，可以“以一边的现有代码为基础，补入另一边的功能和修复”，也可以“合并两边改动，再处理重叠和冲突”。用户未指定时，AI 结合实际分支解释差别、给出推荐理由，等用户选择后执行；已指定则不重复询问，也可明确授权自动判断并执行。提交历史不强求线性。

本技能统一维护在 [agent-git-workflow-skills/lzl-merge](https://github.com/solplum/agent-git-workflow-skills/tree/codex/publish-skills/lzl-merge)，通用技能目录 [lzl-skill](https://github.com/solplum/lzl-skill) 提供索引。

## 使用

在已安装技能的客户端中提出：

> 使用 lzl-merge，把主干合入当前功能分支。自行查清双方意图，核对双方功能、修复和组合逻辑，完成本地合并与验证。提交、推送另行确认。

可明确指定来源分支或固定提交，以及未提交工作是否需要纳入整合。核心只依赖 Git 和项目自己的验证工具，无需额外 MCP 或第三方 skill。

选择提示会写明实际分支、涉及的功能、最终结果交付到哪里，以及为什么推荐某种做法。两种方式都要保留双方仍有效的功能和修复；若预计结果相同，AI 会说明差别主要在整理过程和合并记录，不制造功能取舍。技术名称“基线追加”和“三方合并”放在需要时展开的说明中。

## 安装

先克隆 Git 技能套件：

```sh
git clone https://github.com/solplum/agent-git-workflow-skills.git
```

将其中的 **lzl-merge 子目录**复制或链接到需要的客户端技能目录，保持 SKILL.md 直接位于该目录内：

| 客户端 | 安装位置 |
|---|---|
| Codex | `~/.codex/skills/lzl-merge/SKILL.md` |
| Claude Code | `~/.claude/skills/lzl-merge/SKILL.md` |

已有同名安装时先比较内容并保留必要修改，不要把整个套件当作一个 skill 放入该目录。

也可以保留一份 lzl-merge 子目录，再从两个客户端目录链接到它。Windows 可分别复制该子目录，核心规则不依赖符号链接。当前会话若尚未刷新技能列表，开启新会话后调用。Codex 显示名与技能名均为 `lzl-merge`。

## 工作标准

- 修改前检查覆盖；用普通说法结合当前分支比较两种做法并推荐，未指定时等用户选择，已指定时自行查清细节。区分交付目标与开始整理代码的分支，不默认改写历史。
- 按业务行为保留双方仍有效的能力，允许等价迁移；有意删除的目的同样需要保留。
- 自行调查代码、提交历史、需求和测试；需求矛盾、新规则或责任边界不清时，带证据和建议集中提问。
- 检查实际调用链、数据流、单位、权限、状态、兼容及必要的上下游，处理没有文本冲突的语义错误。
- 验证功能分支、来源分支及双方组合后的关键行为；缺少覆盖时针对具体风险补最小必要的回归验证。
- 保护暂存、未暂存和未跟踪工作，必要时在隔离 worktree 生成候选，并写明未纳入的原有工作。
- 默认交付本地结果和验证记录，提交、推送及发布按本次明确授权执行。默认也不创建隐藏的临时提交。

原生不提交 merge 保留 MERGE_HEAD；基线追加内容候选可以没有 MERGE_HEAD。分别说明内容完成、验证完成、是否已应用目标及历史是否已记录来源。多个来源可围绕完整基线逐步整合内容；只有任务明确要求原生顺序合并且需要中间提交时，才针对具体范围请求授权。

## 验证范围

初版于 2026-10-30 用隔离合成 Git 仓库完成独立前向演练：

| 场景 | 结果 |
|---|---|
| 主干重构与修复、分支新增功能产生文本冲突 | 保留双方行为及组合结果；7 项测试与独立行为检查通过 |
| 无文本冲突，原有测试通过，但契约单位发生变化 | 发现并修复重复换算；6 项测试与独立行为检查通过；原有笔记和草稿逐字节保留 |
| 双方权限需求互斥 | 保留原分支和双方证据，提出业务裁决问题，未擅自放宽权限 |

另验证了可 fast-forward 输入保持待提交状态、简单原生多头合并不提交、复杂多头合并被拒时 HEAD 不变。技能格式校验通过。

2026-11-02 增补基线追加与用户选择流程后，独立演练确认：

- 明确选择基线追加：以重构后的实现为基线迁入另一侧有效功能与约束，保留模块迁移、修复及有意删除；13 项组合测试与独立行为检查通过，原工作树笔记和草稿保持原样，未提交。
- 未指定方式：分析并推荐基线追加，同时提供原生三方合并选项；等待用户选择，未创建候选或修改代码、引用及工作树。
- 将已验证内容候选应用到干净目标：结果树逐项一致，目标 HEAD 不变，未伪造 MERGE_HEAD。

同日将选择提示改为普通说法后，用不熟悉 Git 术语的模拟用户请求独立检查：提示包含实际 main、feature 分支及报价结构、优惠券、金额校验等具体变化，说明交付目标、两种做法的实际差别和推荐理由，并如实说明功能可以相同；执行者等待选择，未修改代码或引用。这是模拟请求检查，未进行普通用户可用性实测。

这些演练说明上述场景的观察结果；真实项目仍需在使用时核对其环境与行为。未另行启动两个客户端的新会话验证加载，不据此宣称所有未知行为已验证。
