# Change Report


## V2：可组合、可恢复的执行模型（优先于下文任何冲突规则）

\`change-report\` 可在 commit 前、push 前、push 后或补记后调用；它不要求固定顺序，也绝不为了凑齐流程而编造状态。

### 报告范围选择

优先级如下：

1. 用户显式指定 \`--record <ID>\`、\`--range <base>..<head>\` 或 \`--commit <SHA>\`；
2. 当前分支只有一条可恢复的本地记录时，使用该记录关联的 commit 与变更日志；
3. 否则展示“未提交改动 / 未推送 commit / 已推送未合并 commit”的候选范围，请用户选择。

不得以“最近 N 个 commit”作为无提示默认范围。指定范围不存在、索引丢失或关联不明确时，退回 Git 与变更日志重建，并明确说明不确定性。

### 报告状态与重复调用

报告须如实标记范围状态：

- \`draft\`：存在未提交改动；
- \`local-commit\`：已有本地 commit，尚未确认已推送；
- \`pushed\`：本地远端跟踪信息或状态索引证明已推送；
- \`unknown\`：无法可靠确认远端状态。

重复调用同一范围时，默认展示或更新 Markdown 草稿。渲染 Word 文件仍要求用户指定输出路径；目标文件已存在时，必须先确认覆盖。成功生成报告后，可将 \`reported\` 与输出路径写入本地状态索引，但不得将该索引或报告内容自动提交、推送。

保留只读 Git 分析、无代码、无敏感信息、不编造原因和验证结果的全部约束。


根据本次 git 改动生成面向上级的正式 Word 变更报告：改了什么、为什么改。全程只读（git status/log/diff），无代码、无敏感信息。

## 前置检查

1. 确认是 git 仓库：`git rev-parse --is-inside-work-tree`，非 git 仓库 → 报错退出。
2. 确认有改动：git status --short 有内容，或主干分支存在 commit（主干见①的检测逻辑）→ 否则提示"没有可报告的改动"退出。

## 工作流

### ① 圈定改动范围

```bash
git status --short          # 未提交改动
# 本功能 commit：比较基准按 origin/main → main → master 顺序取第一个存在的主干
git log origin/main..HEAD --oneline 2>/dev/null || git log main..HEAD --oneline 2>/dev/null || git log master..HEAD --oneline 2>/dev/null || git log HEAD --oneline -5
```

- 展示候选改动清单 → 用户确认/裁剪（可"只看最近 N 个"或指定 commit 范围）。
- 无可用主干分支时回退到最近 N 个 commit（默认 5）。

### ② 读 change-log.md 参照

读 `docs/change-log.md`（若存在）——提取本次改动相关条目作背景/细节参照。不存在则跳过。

### ③ 分析 diff，生成报告草稿

```bash
git diff --stat            # 改动概览
git diff -- <主要文件>      # 细读关键改动（判断模块作用）
git log <主干>..HEAD -p --stat  # 结合 commit message 推断"为什么"
```

生成 4 段报告草稿（见下"报告格式"）。"为什么"三源合成：
- 从 diff + commit message 推断
- 结合会话上下文提取
- 推断不出 → 标"原因待确认"，不得编造
- 验证结果从会话上下文提取本次跑过的测试/检查；无验证记录 → 标"未验证"，不编造。

### ④ 展示草稿，用户确认

展示 4 段草稿，重点请用户确认/补充"大点原因"。用户确认前不落稿。

### ⑤ 委托 docx skill 渲染

将定稿 markdown 交给 `docx` skill 渲染成 .docx：
- 调用 docx skill，传入 4 段 markdown 内容
- 输出路径由用户指定
- 渲染失败 → 保留 markdown 草稿，告知用户手动转换或重试

### ⑥ 报告

输出：.docx 路径 + 报告摘要（一句话目标 + 大点列表）。

## 报告格式（4 段，正式 + 精简）

```markdown
# 变更报告 · YYYY-MM-DD
## 一句话目标
本次完成了<什么>，达成了<什么>。

## 背景
<1-2 句正式书面语：本次迭代在做什么、为什么值得做。>

## 本次改动
**<大点 1：主题>**
原因：<该主题现状的正式问题>
- <小点 a>：<层/位置 + 具体动作 + 作用>
- <小点 b>：<层/位置 + 具体动作 + 作用>

**<大点 2：主题>**
原因：<...>
- <小点 a>：<...>

## 验证结果
- <验证方式 + 结果，1-2 条>
```

**结构规则：**
- 大点：按功能主题聚类（非按目录），1-3 个；原因放大点层，与改动一一对应；超 3 个 → 提示合并或裁剪
- 小点：按依赖链排序（设计/数据库 → 后端 → 前端）；每点 = 层/位置 + 动作 + 作用
- 背景 = 业务总述，只出现一次，不重复大点原因

**风格铁律：**
- 措辞正式书面，不用"我改/为什么改"对话口吻
- 短句、直接、不堆套话；每行 ≤ 25 字；全文尽量一页
- 只有模块位置 + 作用，**绝不出现代码片段、文件行号、命令**
- **绝不写敏感信息**（凭据/token/内部地址）

## 安全铁律

1. **只读**——只用 git status/log/diff，绝不 commit/push/reset。
2. **无代码**——报告含模块级描述，绝不粘贴代码/行号/命令。
3. **无敏感**——绝不把凭据/token/内部地址写进报告。
4. **不编造原因**——"为什么"推断不出标"待确认"，用户确认前不落稿。
5. **输出路径每次指定**——不写死。

## 边界与错误处理

- 非 git 仓库 → 报错退出。
- 无改动可报 → 提示退出。
- 无可用主干分支 → 回退最近 N 个 commit。
- change-log.md 不存在 → 跳过参照。
- docx 渲染失败 → 保留 markdown 草稿，告知用户手动转换或重试。
- 会话上下文只提取与本次改动相关的"为什么"，不泄漏无关内容。
