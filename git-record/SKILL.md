# Git Record


## V2：可组合、可恢复的执行模型（优先于下文任何冲突规则）

本 Skill 不属于固定流水线的一环。用户可以在一次任务中多次调用它，也可以先 push 后补记，或先出报告后再 push；不得因为缺少某个“前置 Skill”而拒绝处理。

### 本地状态索引

将非敏感的流程元数据保存在当前仓库的 \`.git/info/agent-git-workflow-state.json\`。该路径天然不受 Git 跟踪，也绝不暂存或推送。索引只可保存记录 ID、分支、基准 SHA、关联 commit SHA、状态标记和报告路径；不得保存代码、diff、凭据、私有 URL 或敏感文件名。

索引只是便利层，不能替代事实来源。索引缺失、损坏或与 Git 不一致时，必须以 Git 状态、commit trailer、变更日志和用户对话重建判断；重建失败才询问用户。

### 记录的生命周期

每条记录使用 \`CR-YYYYMMDD-序号\`，状态可独立推进：\`open\`、\`recorded\`、\`committed\`、\`pushed\`、\`reported\`。它们不是强制顺序：

- 用户指定 \`--record <ID>\` 时，更新该记录。
- 未指定且当前分支只有一条兼容的未关闭记录时，续写该记录。
- 存在多条可匹配记录时，展示候选并询问；不得猜测归属。
- 没有匹配记录时，创建新记录。
- 分支已有未记录的本地 commit 时，允许补记这些 commit；不得要求先制造新的工作区改动。

### 日志与本地提交

默认日志路径仍为项目既有的变更日志；没有时创建 \`docs/change-log.md\`。默认策略为 **local-log**：可以写入日志，但绝不自动暂存该日志，也不把它带入代码 commit。若该日志已被 Git 跟踪或用户希望协作共享，必须明确提示并取得 \`--share-log\` 或等价确认，才可精确暂存该日志。

每次调用都应保存本次观察到的需求、动作、影响、验证与待确认项。对同一条 \`open\` 记录，应追加增量或更新其检查点，避免复制完全相同的内容。

创建代码 commit 前，先展示精确候选文件、分组和 message；确认后仅暂存代码候选文件。commit message 末尾追加：

\`\`\`text
Record-Id: CR-YYYYMMDD-序号
\`\`\`

commit 成功后，回写本地日志和状态索引中的真实 SHA。这不会产生第二个 commit，因为默认日志未被暂存。

### 模式

- \`--record-only\`：只更新记录和状态索引，不请求或创建 commit。
- \`--share-log\`：经明确确认后，将本条记录的日志文件与对应代码一起精确提交。
- \`--record <ID>\`：继续、补记或定位指定记录。

绝不执行 fetch、pull、push、remote、rebase、merge、reset 或切换分支。


这是 Claude Code `/git-push` 的本地留痕版本：保留“盘点 → 排除 → 审查 → 用户确认 → 精确提交”的安全流程，但只操作当前本地分支。绝不读取 remote，不联网，也绝不执行 `git push`。

一次显式调用对应一次变更会话记录，覆盖当前工作区中全部可安全记录的改动。若改动属于多个互不相关的意图，先按意图分组，请用户确认拆分为多条记录/多个本地 commit，或合并为一次会话。

## 模式与边界

- 默认：写入变更日志，展示候选文件和本地 commit message，等待用户确认后才执行 `git add <path>` 和 `git commit`。
- `--record-only`：只写日志与 Git 快照，不请求或执行 commit。
- 用户可缩减候选文件、改写 message、拆分记录或取消提交；取消不撤回已经写入的日志。
- 只处理用户明确给出的项目路径，或当前工作目录所属的唯一 Git 仓库。多个仓库时先询问，不猜测。
- 只读取完成记录所需的上下文：根目录 `AGENTS.md`、已有变更日志、当前对话、Git 状态、候选 diff、未跟踪文件必要头部及相关局部代码。不要无目的扫描整个代码库。
- 永不记录或暂存 `.env`、密钥、令牌、Cookie、密码、私有 URL、个人数据、凭据文件及其内容。必要时只写“已更新受控本地配置（未记录敏感值）”。
- 不自动修改代码、配置或测试；唯一允许写入的项目文件是目标变更日志。

## 1. 前置检查与工作区盘点

在候选目录运行：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git rev-parse --short HEAD
git status --short
git status --ignored --short
git diff --stat
git diff --cached --stat
git diff --name-only
git diff --cached --name-only
```

1. 非 Git 仓库时报告并停止。
2. `main`、`master` 或 detached HEAD 时停止本地提交流程；仅在用户明确要求 `--record-only` 时写日志。
3. 盘点全部已修改、已暂存、删除和未跟踪文件；未跟踪文件只读必要头部或 README 判断用途。
4. 排除敏感文件、依赖缓存、构建产物、运行时目录、锁文件和明显临时文件；不读取敏感文件正文。
5. 其余改动都是候选记录范围。无法立刻归属时必须标为“待确认”，不得静默遗漏。

## 2. 建立证据与识别未知信息

从当前对话提取用户的目标、约束、已执行动作与验证结果；再以 diff 和必要局部代码验证。每条叙述均标注来源：

- **已确认**：用户明确说明、Git 状态、diff 或实际命令输出直接证明。
- **推断**：从代码、文件名或调用关系合理推导，但对话未明确说明；必须写明依据。
- **待确认**：改动存在，但无法确定目的、影响或是否属于同一任务。

未知信息不能伪造为已知事实。将下列信号记为可追踪的“待确认”：对话未提及的改动文件、未运行验证的相邻调用路径、不可安全读取的文件、混杂的多项改动、代码与描述或验证结果相互矛盾。每个待确认项都写清“观察到什么、依据是什么、尚不知道什么、下一步如何确认”。

## 3. 复用或创建项目变更日志

按顺序定位，找到后必须完整读取：

1. `docs/change-log.md`
2. `docs/CHANGELOG.md`
3. `CHANGELOG.md`
4. `docs/changes.md`

均不存在时创建 `docs/change-log.md`：

```markdown
# 变更日志

> 记录需求、实际动作、验证、发现与待确认项，以及本地 Git 状态。
```

继承项目既有的语言、标题层级和排序。倒序日志在首个历史条目之前最小化插入；写入前再读一次，避免覆盖并发新增内容。

默认模板（已有等价字段时沿用项目格式）：

```markdown
## YYYY-MM-DD — <简短改动主题>

### 需求
- [已确认] <用户要解决的问题、目标与约束>

### 动作
- [已确认] `<相对路径>`：<实际修改>
- [推断] `<相对路径>`：<推断的作用；依据：...>

### 影响文件
- `<相对路径>`（新增 / 修改 / 删除；已确认 / 待确认）

### 验证
- `<实际执行命令或检查>`：<真实结果>
- 未运行：<原因>。

### 发现与待确认
- [待确认] <观察到的信号>；依据：<diff / 状态 / 调用路径>；下一步：<如何确认>

### Git
- 分支：`<branch>`；记录前 HEAD：`<short SHA 或 unborn HEAD>`。
- 候选范围：<安全候选文件数与路径概括>。
- 已排除：<仅类别与原因，不泄露敏感路径或值>。
- 本地提交：待用户确认 / 未请求（record-only）/ 与本条记录同一 commit。
```

`需求`回答“为什么做”，`动作`回答“实际做了什么”。影响文件必须覆盖全部非敏感候选改动和日志本身；未知归属也要列出并标为待确认。不得声称未执行的测试已通过，也不得复制大段 diff 或敏感信息到日志。

## 4. 审查、分组与本地提交

对每个候选文件运行精确范围的 `git diff -- <path>` 或读取必要局部内容，归类为 `feat`、`fix`、`refactor`、`docs`、`style`、`perf`、`test` 或 `chore`。先向用户展示：

1. 已排除项及原因；
2. 候选文件清单与按意图分组；
3. 变更日志拟写标题；
4. 建议的 Conventional Commit message：`<type>(<scope>): <中文 subject>`。

若候选文件可可靠分成多个独立意图，先询问是拆成多条日志/多个本地 commit，还是合并。文件无法归类时停止提交，保留日志中的待确认项并请用户决定；不得猜测或静默纳入。

在用户确认精确文件列表、分组方式和 commit message 前，已允许写日志，但不得执行 `git add`、`git commit`、`git reset`、`git checkout`、`git stash` 或切换分支。

确认后，对每个分组执行：

```powershell
git add -- <选定的相对路径...>
git commit -m "<确认后的 message>"
git status --short
```

- 绝不使用 `git add -A` 或 `git add .`。
- 目标变更日志可随对应本地 commit 一起暂存，即使它在 `docs/`；这是相对云端 `/git-push` 的显式例外。
- 不把 commit SHA 回写到同一条日志，避免为写入自身 SHA 创建无意义的第二次 commit；最终答复报告真实 SHA。
- 绝不执行 `git remote`、`git fetch`、`git pull`、`git push`、rebase、merge 或 force 操作。

## 5. 完成报告

报告目标仓库、日志路径与标题、已记录分组与待确认项、排除类别、最终 Git 状态，以及每个本地 commit 的 SHA 和 subject。若选择 `--record-only` 或不确认提交，明确说明日志已写入但 Git 未提交。
